Casper / Slack / Pi

How Plan Mode and ask_user reach Slack

Two different local extension APIs share the same transport: pi-casper listens inside the Pi session, forwards structured events to a broker daemon over a local socket, and the daemon owns all Slack Socket Mode and Web API calls.

Architecture

The shared bridge

Neither the coding agent nor normal extensions get Slack tools. pi-casper is the only local extension that talks to the Casper daemon, and the daemon is the only process that talks to Slack. Plan review and ask_user differ mainly in which extension owns the pending local decision.

Plan mode

Decision owned by pi-plan-mode

  • Registers a pending plan-review prompt in a global bridge.
  • Emits pi:plan-mode:ready when exit_plan_mode presents the HTML plan.
  • Consumes approve, refine, or exit decisions.

ask_user

Decision owned by pi-ask-user

  • Registers a pending question prompt in a global bridge.
  • Validates Slack button/modal answers with the same internal parser.
  • Resolves the local tool call when Slack submits a valid response.

Casper

Transport and Slack ownership

  • pi-casper forwards structured events over a local socket.
  • The daemon posts Block Kit, opens modals, uploads PDFs, and receives interactions.
  • Slack action results flow back to the local extension that owns the decision.

Sequence

Plan mode review flow

Plan mode is a review gate around an HTML plan artifact. Slack never edits the plan directly; Slack sends a decision back to the local pi-plan-mode bridge.

Slack controlDaemon behaviorLocal outcome
Approve and executeSends plan_action with action: "approve".pi-plan-mode approves the current plan and triggers the execution turn.
Request changesOpens a Slack modal, extracts text feedback, then sends plan_action with action: "refine".pi-plan-mode injects the feedback as a local user message. The agent revises the same plan file and presents it again.
Exit plan modeSends plan_action with action: "exit".The local plan review prompt resolves with exit and the Slack card is completed.

Sequence

ask_user question flow

ask_user is a tool prompt, not a plan artifact. The local pi-ask-user extension remains the source of truth: Slack submits a structured response, then pi-ask-user validates it and resolves the waiting tool.

Question shapeSlack UIWhy
One question, 1–5 options, no multi/freeform/commentDirect Block Kit buttonsFast path. Each option button has a unique action ID and a JSON value containing the full prompt ID.
Multiple questions, multi-select, freeform text, comments, or larger option setsSlack modalThe modal can collect structured fields that map back to pi-ask-user question objects.

Host/harness-only prompt without bridge metadataFallback notice onlyCasper can display that input is needed, but the local runtime must answer it.

State and safety

What keeps questions from double-submitting

Both flows use an in-memory pending map on the daemon plus a pending bridge in the local extension. A Slack action is accepted only when the card still matches the active local prompt.

Prompt identity

Full IDs stay intact

  • ask_user prompt IDs can contain |, so direct button values are JSON.
  • The daemon stores promptId and a toolCallId → promptId alias.
  • Plan reviews use sessionId:planFilePath as the review ID.

Race guards

One prompt per tool call

  • tool_execution_start schedules a delayed ask forward.
  • tool_execution_update can also forward.
  • forwardedAskUserToolCalls is set before async waits, so only one path posts.

Slack card state

Buttons disappear while submitting

  • The daemon marks a card submitting before sending the local action.
  • Submitting and completed cards ignore repeated clicks quietly.
  • Successful results update the card to handled/submitted.

Mental model

One sentence version

Plan mode asks, “Should this plan execute?” The pending decision belongs to pi-plan-mode, and Casper makes a Slack review card for it.

ask_user asks, “What answer should this waiting tool receive?” The pending decision belongs to pi-ask-user, and Casper makes a Slack button/modal surface for it.

In both cases, Slack is only the remote UI. The local extension validates and resolves the decision.
